# Wren AI Agent 案例研究：改寫大綱

重寫理由：目前正文的敘事是「看數據 → 得出洞察 → 做對的事」一條直線，但結尾的
Hindsight 承認真實過程是「先做了改版，才發現方向錯了」。正文與結尾互相矛盾，而且
真實版本比較好看，卻被降級成一句反省。這份大綱把那條真實路徑扶正成主線。

**主軸一句話**
產品裡最有價值的行為，是最少人完成的。我先做了理所當然的改版，然後用自己做的數據
否定它，最後把「教 AI」整個搬進使用者唯一記得的入口，也就是輸入框。

## 01. 悖論：最有價值的動作，最少人做完

**目的**：不解釋產品有幾個入口，只把一個矛盾放到讀者面前。

**內容**
- Knowledge 是什麼：團隊把自己的指標、定義、業務規則寫下來，Wren 才答得準。
- 它是付費訊號最強的行為之一：有建 Knowledge 的使用者轉換率 0.7%，沒建的 0.1%，
  約 7 倍。
- 它同時是最少人完成的：只有約 10% 的團隊建過任何一條，而且整年一路下滑。
- 收束：在所有能量測的行為裡，最有價值的那一個，幾乎沒有人做完。

**素材**：現行 s03 的兩個 num-row 與那張 paid-rate 圖表整段前移。現行 s01 的
「Knowledge 是最少用的功能之一」也併進來。

**要新寫**：一段 lede，把矛盾講清楚。現行 s01 的 lede（關於觀察行為勝過詢問）
移到 02 節用。

## 02. 我先做了改版，然後數據把它殺了

**目的**：本篇的轉折。這節決定整篇是「乾淨的推導」還是「有判斷力的過程」。

**內容**
1. 我先做了理所當然的事：更好的範本、批次匯入、友善的空狀態。前提是「使用者
   在頁面裡卡住了」。
2. 為了驗證這個前提，我挖了 90 天的產品數據（Langfuse、PostHog）：
   - 近 18,500 次互動中，91% 發生在同一個輸入框，十幾個功能入口加起來不到 10%。
   - 582 位活躍使用者中，72% 從未碰過任何功能入口，最熱門的入口也只有 14% 的人用過。
   - 20 段 session 錄影裡，13 段顯示使用者在選單間迷路，路徑是「點進去、退出來、
     再試另一個」。
3. 前提被推翻：使用者不是在頁面裡失敗，是根本沒有抵達。打磨一個沒人走進來的
   目的地，動不了一個由缺席驅動的數字。

**素材**：現行 s01 的三個 num-row 整段移來。現行 s03 的「Rebuild the Knowledge
page as a smarter form」那個 rejected design 升格成本節的第 1 段。

**寫作提醒**：不要寫成「我浪費了幾週」，要寫成「我驗證了預設解法並用數據否定它」。
殺掉改版的正是自己做的數據分析，這是嚴謹不是失誤。

## 03. 他們早就在做的事

**目的**：把「不是改版」轉成「那該做什麼」。

**內容**
- Evidence 01：旁邊就有按鈕，使用者還是選擇打字。「生成圖表」「幫我做報告」
  「改成折線圖」。自然語言不是退路，是第一直覺。
- Evidence 02：試用者直接在輸入框打「what can I ask?」。沒有人翻選單學怎麼用產品。
  在使用者心裡，輸入框就是整個產品。
- Evidence 03：重度使用者直接把資料庫欄位名寫進句子，精準度比新手高約 12 倍。
  而這些超級明確的請求失敗時，95.9% 是因為舊架構接不住（NO_RELEVANT_SQL）。
- 收束：瓶頸從來不是使用者的表達，是產品的接收。
- 決定：與其重新教人按鈕在哪，不如把每一個能力都重建成住在對話裡的 Skill，
  而且從最難搬、價值最高的那一個開始：教 AI 這件事本身。

**素材**：現行 s02 三個 evidence 與 pivot 段落，幾乎可原樣沿用。

**要修**：pivot 段目前寫「這個結論不是我們發明的，是使用者投票投出來的」。在新結構
裡前面已經演過失敗的改版，這句要調整語氣，否則會像是從沒走過彎路。

## 04. 用講的教 AI

**目的**：交付物本身。

**內容**
- Before：業務邏輯要在專屬頁面一條一條手動輸入，與需求發生的當下脫節。你得離開
  問題去做設定，再回來。多數團隊沒做完，AI 就一直只被教了一半。
- After：像交代同事一樣用講的。「活躍客戶是指至少有一筆未取消訂單的人。」Agent
  用選擇題確認它聽到什麼，草擬成 markdown，再問你要怎麼處理。
- 四個 shipped moments（沿用現行四段 figcaption 與影片）：
  1. 收斂，不猜測。
  2. 存檔前確認。
  3. 頁面沒有消失，它變成稽核介面。
  4. 迴圈閉合，Agent 回答時會指名它套用了哪一條規則。
- 拒絕的設計：讓 Agent 靜默儲存它推論到的東西。因為 Knowledge 是共用基礎建設，
  一句聽錯的話會安靜地污染每個同事的答案。草稿加上明確的「發布」閘門，用一次點擊
  換到可稽核性。
- 收束：如果連教學這種全產品最像設定的任務都能塌縮成對話，那其他都可以。

**素材**：現行 s03 後半整段沿用。rejected design 只留「靜默儲存」這一項，另一項
已升格到 02 節。

## 05. 每個功能都是一個 Skill

**目的**：從一個功能放大成架構。

**內容**
- 舊的線性架構裡，報告生成、資料評估、文件解析散落成按鈕與專屬模式，推高工程成本
  也打斷心流。
- 重新定義 Official Skills，把後端邏輯封裝成原子能力模組。
- 最深的設計意涵：所有能力塌縮到同一套觸發語法，呼叫任何一個都只是輸入框裡的一句話。
  Skill 的撰寫與治理仍然是一個真實介面，但沒有人需要「找到」功能才能用它。
- 六個 Official Skills 表格沿用。
- 買到的是：單一路由層，以及一組可以成長而介面不必跟著長大的能力集合。

**素材**：現行 s04 幾乎原樣，含 journey card 與 Skill 表格。

**要修**：現行這節的 HTML 有幾處小標題與內文黏在一起（例如「Unified routing:」
與前段沒有斷開），順手修掉。

## 06. 結果，以及這個架構讓什麼變難了

**目的**：收尾。前半沿用，後半換掉。

**內容（前半，沿用）**
- 使用者不必再學地圖：上線一個月內，舊入口使用量從每月數百次掉到個位數，沒有人
  要求切回去。早期回饋讚踩比約 4:1。
- 新功能不必動 UI：發一個新 Skill 就好，沒有新按鈕、新頁面、新教學。UI 開發從
  每個功能的固定成本，變成一次性的架構投資。
- 統一語法打開生態：使用者自訂 Skill 與 Official Skill 遵循同一套規則，擴充能力
  不再只是產品團隊的事。

**內容（後半，需要新寫，取代現行 Hindsight）**
現行結尾「我太早跳進改版」在新結構裡已經是 02 節的主線，會變成冗語。建議換成
承認取捨，這比再列一項好處更有份量。

最現成的角度：Evidence 02 埋了一個沒被回答的問題。使用者會直接打「what can I ask?」，
當按鈕全部消失、所有能力都收進輸入框之後，這個問題不會消失，反而更尖銳。

**已解決（2026-08-24，Iris 提供）。** 產品一開始就有引導，而且做法與整個架構一致：
發現能力這件事也被搬進對話裡，不是把選單加回去。首次使用會開一個名為
「Explore workflow-boosting features」的對話，Agent 主動列出四張能力卡片
（GenBI Apps、Agent skills、Knowledge、Generate reports），每張可展開成預覽，
「Try it out」直接在對話裡把流程跑起來，而不是打開設定頁。

素材來源：`assets/wren-agent/sources/Knowledge.mov` 的 2 至 20 秒。這段原本沒有
被任何剪輯用到，內容正好是引導面板、展開 Knowledge、送出請求，接著就銜接到
33 秒開始的 teach-clarify。已剪成 `assets/wren-agent/onboarding.mp4`。

Figma 來源：Main Feature Home，node 9161-34853。

因此 06 節的收尾改為「讓什麼變難了，以及我們怎麼處理」，先講問題與解法，放影片，
再收在仍然開放的部分：精選卡片回答得了抵達當天的問題，但 Skill 架構的用意就是
能力會持續長大、而且自訂 Skill 把作者權交給使用者，一份固定的歡迎清單追不上。
